Anatomy of a Vanishing Cookie

Why @svelte-atproto/oauth loses the oauth_return_to cookie, why an organizer signing in at /organizer got dumped on the survey — and why our fix writes a Set-Cookie header by hand instead of asking the library nicely.

@svelte-atproto/oauth ^0.3.0 @sveltejs/kit 2.50.2 Fixed in PR #6 · src/hooks.server.ts

The whole bug in two sentences

event.cookies.set() doesn't put a cookie on any response — it puts a note in SvelteKit's cookie jar, and SvelteKit only empties the jar onto responses it builds. The library's login handler builds its own Response and returns it straight from the handle hook, so the jar is never emptied, the browser never receives oauth_return_to, and the OAuth callback falls back to redirecting to /.

1Like you're five

The kitchen (SvelteKit) has one rule: every box that leaves the shop goes through the packing table (resolve()), and the packer tucks in whatever cookies are on the sticky-note list (event.cookies.set() writes to that list).

The OAuth library is a guest baker. When you ask to log in, it writes on the sticky-note list — "please pack a cookie that says /organizer" — and then it packs its own box, seals it, and walks it out the side door. It never passes the packing table.

The note is still on the list. The cookie is still in the kitchen. The box is gone. When you come back later and the shop asks "where were we sending you?", your hands are empty, so it shrugs and sends you to the front door: /.

Everything below is just this story with file names and line numbers.

3Two cookies, two fates

The confusing part of this bug: the library sets its session cookies with the exact same cookies.set() API, and those work fine. Only oauth_return_to vanishes. The difference isn't the cookie — it's how each handler exits.

  2. Library queues the cookie in the jar.index.mjs:228 — cookies.set(COOKIE_RETURN_TO, …)

Same jar, same API. One handler exits by throwing, so SvelteKit builds the response and packs the cookies; the other exits by returning a finished response, and nobody packs anything.

5Your actual question: why does the fix build the header by hand?

Our returnToFix hook sits in front of the library in the sequence(). When it calls await resolve(event), that "resolve" is just the next link in the chain — it runs the library's handle, which returns the sealed json({ url }) box from line 351. So the fix is now holding a finished Response object, and at that point there are only bad options and one good one:

  • "Use event.cookies.set() ourselves" — queues into the very same jar nobody will ever empty. The real resolve() (line 478) never runs for this request, because the chain short-circuited at the library. Same bug, now written by us.
  • "Use the library part that formally adds the cookies" — there isn't one for a response it has already returned. The library's cookie helpers (cookieOptions, setSignedCookie) aren't exported, and even if they were, they also just call cookies.set() — they write sticky notes too. The library has no code path that stamps a cookie onto an existing Response; the "formal" machinery it relies on is SvelteKit's, and SvelteKit is out of the loop the moment line 351 returns.
  • The one interface a finished Response actually has: its headers. So we do, by hand, precisely what add_cookies_to_headers would have done — append a serialized Set-Cookie header:
src/hooks.server.tsour fix
79const response = await resolve(event);   // ← the library's sealed box comes back here…83const safe = response.ok && returnTo ? safeReturnTo(returnTo, event.url.origin) : null;84if (safe) {87    response.headers.append(88        'set-cookie',89        `oauth_return_to=${encodeURIComponent(safe)}; Path=/; HttpOnly; SameSite=Lax;${dev ? '' : ' Secure;'} Max-Age=600`90    );91}92return response;
Hand-rolled because we're downstream of the side door: once a Response exists, headers are the only way in. The attributes deliberately mirror the library's own (index.mjs:228–234), including Secure-only-in-prod.

One nuance in there: we read returnTo from a clone of the request body before resolving (the library consumes the original), and we re-encode with encodeURIComponent because the library's callback runs decodeURIComponent on whatever it finds in the cookie (index.mjs:311).

So, in one line

The fix hand-builds the header because the "formal" cookie machinery is a queue, not a stamp — and for this request, the only worker who ever empties the queue went home when the library returned its own response.

6Bonus bug we fixed while in there

The library's own safety check for returnTo is a prefix test (index.mjs:213–222): starts with /, doesn't start with //. That admits /\evil.example — and browsers normalize backslashes in Location headers, so it resolves to https://evil.example. An open redirect.

The hole

isSafeReturnTo("/\\evil.example") → true in the library. Our safeReturnTo() (hooks.server.ts:43–57) rejects backslashes outright and resolves the decoded value against our origin with new URL(decoded, origin).origin !== origin, which catches the whole class, encoded forms included.

7What upstream should do

For the issue write-up, the library has three clean options — any one of them fixes it:

  • Attach the header directly in the login handler: build the Set-Cookie string and put it on the json() response it's already constructing (what our workaround does from outside).
  • Exit by throwing: SvelteKit empties the jar for thrown redirects (respond.js:421) — the callback handler proves this path works. Less natural for a JSON endpoint, but it's why half the library already behaves.
  • Ship real routes instead of intercepting inside handle: responses from +server.ts endpoints come out of resolve() and hit line 478, so cookies.set() would just work — and this is the fix that also makes every future cookie in the library safe by construction.
  • Separately: harden isSafeReturnTo against backslash normalization (reject \, resolve against origin).
